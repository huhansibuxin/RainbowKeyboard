# RainbowKeyboard

彩虹键盘光效越狱插件。`1.2.1` 在 17.10 基板之上做热路径收尾，并回退 1.2.0 中一项会复现 17.9 的几何判定改动。

## 1.2.0 基板热路径收尾（观感不变）

回退说明：`1.1.5` 试图把中英/123/符号三个换键面键的闪光改成「切换完成后在新键位闪」，
实机不可靠（中英切换不改变键帽数，判定门根本不触发；123 则两种时序都有），已整条撤销，
重新以 17.10 为基板。本版只做下面六项，不含任何行为改动。

| # | 项 | 改前 | 改后 |
|---|---|---|---|
| 1 | 配置刷新 | 每次按键：1 次加锁 + 跨进程查询 ×2 | 设置页保存时推送；按键路径只剩 1 次浮点比较（另有每秒一次兜底重查） |
| 2 | 参数取值 | 每次按键约 42 次取值 = 84 次字典查找 + 42 次类型探测 | 配置变更时一次解析成扁平数值，绘制路径直接读 |
| 3 | 键缝遮罩层 | 每次按键新建一个 `CAShapeLayer`（路径已缓存） | 复用同一个层 |
| 4 | 布局代际 | 宿主**每次**布局都前移 | 只在**键区尺寸变化**或**有未登记过的键帽登记进来**时前移 —— **1.2.1 已回退，见下节** |
| 5 | 注册表遍历 | `allObjects` 每次都分配一个数组 | 直接枚举，零分配 |
| 6 | 轻弹键帽轮廓 | 每次按下重渲染 + 逐像素提取 | 仅当重新渲染出的位图与上次**逐字节相同**时复用；逐像素只处理能带墨的像素 |

**第 6 项为什么可以缓存而不怕取到过期字形**：缓存的判据是「重新渲染出的位图逐字节相同」，
不是「同一个键」。大小写切换、中英切换都会改变字形像素，因此字节不同就必然重新提取。

## 1.2.1 回退布局代际收窄（1.2.0 复现了 17.9）

**现象**（实机）：九键打字正常；切到英文也正常；**再切回九键，光效的物理命中区域仍是英文那套**
—— 也就是切换过中英之后，键位表最终停在英文布局。

**根因**：1.2.0 把「布局代际」的触发条件收窄成「宿主 bounds 变化」或「有未登记过的键帽登记进来」，
本意是让「不移动任何东西的重布局」不再作废键位表。但微信键盘**两套键面的键帽在切换时都已经登记**
（旧键面被收进隐藏容器但对象仍活着），于是：

- 切回九键 **不会**有新键帽登记 ⇒ 代际不动；
- 注册键帽数**也不动** ⇒ 作为独立兜底的「注册数」判据同样不动。

两个收窄后的判据同时沉默，而键位真的换了 ⇒ `updateKeyFramesForHost:` 判定「没变」，
继续复用英文那套键位表。（去程九键→英文能生效，是因为英文键帽是**第一次**登记。）

**修复**：布局代际恢复为**宿主每次布局都前移**（回到 17.10 的语义）。
「连续打字不重算键位表」这件事本来就由**门**负责（代际/注册数/尺寸三者都没动才复用），
不需要靠收窄代际来实现，所以回退不损失什么。

**其余五项（配置推送式、参数一次解析、遮罩层复用、注册表直接枚举、轻弹轮廓可复用）不受影响。**

## Samsung17.10 候选词变色自行开启

**现象**：没有主动打开候选词变色，但选择「自定义」、或配置回落到内建值之后，
候选词变色变成开启状态并实际生效。

**根因（两处叠加，缺一不可）**：
1. 候选开关的判定语义是 **「键不存在 = 视为开启」**
   （`CandidateGradient.xm` 旧实现 `!prefs[key] || [prefs[key] boolValue]`）。
2. 而「自定义」与回落状态**恰好都不写这三个键**：
   `RKRestoreCustomParameters()` 只恢复 19 个参数键；
   渲染层回落表 `RKPresetSelfUseTable()` 也不含候选键。
   更隐蔽的是 `RKDisplayTransport.h` 的 `RKMergeDisplaySnapshot()` —— 它先
   `removeObjectsForKeys:RKDisplayKeys()` 删掉本地全部显示键，再用 notifyd 快照覆盖；
   快照里没有这一位时，合并结果里**这个键就消失了**，于是被判为「开启」。

**修复**：
- 判定语义反转为 **「必须显式开启」**（键缺失即为关）。
- 设置页三个候选开关的 `default` 从 `<true/>` 改为 `<false/>`，显示与实际生效不再矛盾。
- 主开关做成缓存（`RKCandidateTintMaster`）：关闭时每次文本绘制只读一个标志位，
  不做字典查找；三个绘制钩子本身保留，手动开启时功能照常可用。
- `RKDisplayKeys()` 的位置型位域**一个元素都没动**（删元素会让后续位号前移，
  重演 17.3 那次光效全灭）。

**验证**：`rk_perf/verify_candidate_off.py` —— 从源码抽键表做 7 组仿真：
三个「缺键」场景在旧实现下全部变开（复现现象）、新实现全部保持关；
显式 True 时功能仍可用；键盘扩散的 flag 语义未被波及。

## Samsung17.9 键位布局切换后光效几何不刷新

**现象**：用微信键盘从九键切到全键盘，按一个字母，光效仍从原来九个数字键的位置扩散；
有时甚至完全没有光效。九键本身、以及一开始就在用的那种布局，都是正常的。

**根因**：光效视图的键位表只在 `host.bounds` 变化时才重建（`Tweak.xm` 里
`geometryChanged = !recordedBounds || !CGRectEqualToRect(recordedBounds, host.bounds)`）。
而**切换键位布局不改变键盘区的尺寸** —— 九键和全键盘占用同一块区域，`bounds` 逐字段相同。
于是判断恒为 false，键位表一直停留在做九键时收集的那一套。

扩散原点也不是触点，而是从键位表里找**离触点最近的那个键的中心**
（`RainbowEffectView` 的 `showKeyWaveAtPoint:`）。旧表里没有字母键：触点到最近的
九键大键超过 14pt 就整场不出光效；落在某个大键覆盖范围内时，`origin` 便取那个数字键的
中心 —— 于是看起来“从那九个数字那里扩散”。

**修复**：

- **指纹改为三项**（`RainbowEffectView` 的 `updateKeyFramesForHost:`）：`host.bounds` +
  **host 布局代际**（`RKKeyboardLayoutStamp()`，由 host 的 `layoutSubviews` 钩子递增）+
  **注册键帽数**（`RKRegisteredKeyCount()`）。三项都是 O(1) 读取、零对象分配。换布局必然
  至少改动其中一项；同一布局连续打字三项全不变；既修掉错位，也不把“每次按键都重算几何”
  的开销引回来。
- **淘汰旧布局的键帽**：微信用“把旧布局整块容器隐藏”的方式收纳，键帽自身的 `hidden`
  仍是 NO、`alpha` 仍是 1，原来的自检过不了这一关。`RKKeyViewIsLive()` 改为沿短链上溯
  到 host（2~3 级固定深度，不递归、不匹配类名），链上任何容器隐藏或透明即淘汰；并额外
  要求键帽与 host **同窗口**，排除停在预载窗口里的键帽（其坐标转换会算出貌似合理的数值）。
- **兜底**：严格判定若一个键都留不下，退回宽松判定 —— 丢掉全部键会让光效彻底消失，
  比几何错位更糟。
- **宿主取值同样加校验**：隐藏/离屏的 host 实例不再抢占指针，也不会被当成可用宿主。

**校验**：`rk_perf/verify_layout_switch.py` —— 源码静态一致性 33 项 + 状态机仿真。
仿真复现了旧判据不重算、按下 q 得到九键位置／无光效，并验证新判据重算后扩散原点精确
等于被按下的那个字母键中心（nearest 0.0pt）；另附“同一布局连打 100 次 → 重算 0 次”的
性能回归护栏。

## Samsung17.8 自用预设

- **背景**：注入范围收窄到原生键盘（InputUI）与微信键盘扩展（wxkb_plugin）之后，
  SpringBoard 不再注入，而跨进程状态的重建（relay）原本挂在 SpringBoard 上。结果是
  注销/重启后 notifyd 里的状态为空，键盘进程只能各自去读已保存的 plist；读得到就正常，
  读不到就落到代码里的出厂回落值 —— 那套值接近「鲜艳彩虹」，这就是重启后观感变样的原因。
- **做法（不引入第三个进程）**：把当前这套参数固化成预设「自用」，并让它同时充当
  **渲染层的出厂回落值**。两条可能的结果都通向同一套数字，因此无需重建 relay。
- **单一来源**：`RKPresetSelfUseTable()`（`RKPreferences.h`）。设置页的「自用」预设直接
  引用它，`RainbowEffectView` 的 `number:fallback:low:high:` 也让位于它。两边取值不可能漂移。
- **编号兼容**：「自用」用**新编号 4**，柔和/鲜艳/快速/推荐仍为 0/1/2/3。预设编号会持久化
  进 plist，插入到列表最前面（柔和水波之前）若沿用 0 会让所有已保存的选择改义，故取新号。
  显示顺序由 plist 的 `validValues` 数组决定，与编号无关。
- **取值**：逐项照抄设备 plist 的实时值，保留尾数（如 `0.8033448457717896`），不做取整 ——
  这套预设存在的意义就是复现当前观感。校验脚本 `rk_perf/verify_preset.py` 逐键比对源码表与
  设备 plist，并断言三条不变量：表内每个键都在备份键表里、自用在柔和水波之前、旧编号未位移。
- **设置页显示**：`readPreferenceValue:` 在键缺失时也返回同一张表的值，所以“滑条显示的数”
  与“键盘实际用的数”始终一致。

## Samsung17.7 按键热路径瘦身

审计顺序：先看系统侧有没有能耗裁决 → 再看 dylib 静态规模 → 最后逐项数热路径的对象分配。

- **系统能耗裁决与本插件无关**：`wxkb_plugin.wakeups_resource-*.ips` / `wxkb.*.ips`
  中 `grep -c 'RainbowKeyboard|TweakInject|ellekit'` 均为 **0**，且 heaviest stack
  是 `dyld → Foundation/PlugInKit → UIKitCore → GraphicsServices → CoreFoundation
  → mach_msg_trap` 的标准 runloop 等待路径，`Action taken: none`（只记账未处置）。
  事件时间 09-18，早于本版本安装时间，属微信键盘自身的扩展宿主唤醒。
- **dylib 静态规模可忽略**：2 个 ObjC 类 / 183 selrefs / 30 classrefs，vmsize 128 KB，
  8 条 `LC_LOAD_DYLIB` 全是宿主进程本来就有的框架。dyld 登记成本不是问题。
- **源码扫描无阻塞**：无 `dispatch_sync` / 信号量 / 文件 IO / 目录遍历。
- **真正可消除的是重复分配**，两处：
  1. `CAKeyframeAnimation` 的 `keyTimes` / `values` 与 `CAGradientLayer` 的 `locations`
     全是常量，但旧代码每次按键都重建（含数组里每个 `NSNumber`）。这些数组不可变、
     Core Animation 只读取，改为共享一份。背景霓虹两趟共省 4 组动画常量数组；
     每个参与动画的键再省一组 `fade.keyTimes`。
  2. `keyGutterMask` 的复合路径只取决于 `bounds` 与 `keyFrames`，旧代码每次按键都把
     全部键面（约 32 个圆角贝塞尔路径）重新构建一遍。改为按 `bounds` 缓存，
     `setKeyFrames:` 与 bounds 变化时失效（`dealloc` 释放）。
- **量化（逐项对应源码分配语句的对象账）**：

  | 场景 | reach(pt) | 参与动画键数 N | 改前对象/次 | 改后对象/次 | 降幅 |
  |---|---|---|---|---|---|
  | 出厂默认 180 / 2.0 | 180.0 | 19.4 | 555 | 373 | **-33%** |
  | 设备实测 126.26 / 1.5 | 94.7 | 7.9 | 291 | 166 | **-43%** |
  | 半径小 / 扩散大 126.26 / 2.0 | 126.3 | 12.3 | 391 | 245 | -37% |
  | 全部拉满 360 / 3.0 | 540.0 | 32.0 | 844 | 599 | -29% |

  说明：N 由 `reach = BackgroundRadius × Spread / 2` 决定，所以成本与「最大半径」
  「扩散倍率」两个滑条强相关 —— 当前设备参数已把成本压到出厂默认的约 45%。
- **刻意不改的项（已排除，不再重复怀疑）**：
  - `RKReadEffectivePreferences()` 每次按键有 2 次 `notify_get_state` + 1 次
    `notify_check`（约 30~90 µs）。节流可省，但会把「改设置后下一次按键即生效」
    变成最长 100 ms 延迟，收益与体验不成比例，故保留。
  - `halo` 的 shadow 每层一次离屏合成 —— 那是光晕本身，去掉就是改观感。
  - 轻弹模式的字形截图（`RKPressForeground` 的 render server 取图）是唯一未量化的
    毫秒级项，但仅在该模式下执行；当前设备用的是三星风格扩散，不在此路径上。

## Samsung17.6 自定义参数备份

- 根因：效果预设与「自定义」写的是同一批参数键。预设直接原地覆盖 `Opacity` /
  `Brightness` / `Duration` / `EffectStyle` 等 15 个键，而 `Preset = -1`（自定义）
  本身不承载任何数值，只是一个「被手动调整过」的标记位。因此从预设切回「自定义」
  只会改标签，参数仍是预设的；只有之后再随手拖一次滑条，`Preset` 才会再次变成
  `-1` 并带上新数值 —— 这就是该现象时有时无、看起来像随机失效的原因。
- 修复：预设生效前，先把当前这 15 个参数存入 `CustomParams`；选择「自定义」时整体
  还原。仅当被替换的状态确实是自定义（`Preset == -1`）或从未建立过备份时才写入备份，
  避免预设 A 覆盖预设 B 时把 A 的数值误存成自定义。
- `CustomParams` 刻意不进入 `RKDisplayKeys()`：该显示通道是位置型位域，而它是字典，
  登记进去会让其后所有位号位移，重演 17.3 的错位故障。
- 全新安装后首次选预设会用当前（默认）数值播种备份，保证「自定义」始终有值可还原。
- 首次升级到本版本时，若此前从未建立过备份，需先手动调整一次任意滑条再选「自定义」，
  备份即建立；此后切换预设与自定义均为完整还原。

## Samsung17 原生键盘状态刷新

- 原生 `UIKBKeyplaneView` 的状态切换只刷新实际返回的当前键视图，不再每次状态变化遍历最多 512 个键盘视图。
- 同一轮状态切换中的嵌套回调会合并为一次局部刷新，避免 `setState` 两套接口重复处理同一副键盘。
- 原生按键按下/松开不再触发整副键盘键位几何重算；布局、语言切换和键盘结构变化仍保留完整初始化路径。
- 微信输入法不进入这些原生状态 hook，原有微信输入法效果与性能路径保持不变。
- 新增原生状态性能回归，验证 200 次嵌套状态切换只刷新命中的键，并检查纯黑、自定义颜色和按下/松开恢复。

## Samsung16 输入性能

- 触摸事件只在按下时处理，不再对移动、松开、取消事件重复执行整键盘遍历和遮罩重建。
- 键盘效果视图缓存键盘 bounds、实际键位几何和排除遮罩；尺寸未改变时连续输入复用缓存。
- 创建效果视图后把纯黑键盘重刷移到后续主线程回合，避免在输入事件同步路径上执行大批量图层、图片和状态刷新。
- 轻弹模式优先使用触摸对应的当前键视图，只对该键视图做局部字形提取，不再绘制整副键盘。
- 本机无法直接运行用户的巨魔/越狱 App；已用原生键盘测试宿主、复杂键盘图层和模拟器回归验证，其他插件冲突仍需真机确认。

## Samsung15 纯色灯光

- 轻弹模式使用单个 `CALayer.backgroundColor` 均匀填色，取消渐变、高光和边框亮度差异。保留原有字形保护、短促弹簧、消退、同键去重和层数上限。
- 新增 `PressColorMode`：0 彩色（默认）、1 单色。彩色每次有效点击推进色相，当前单键只用一种饱和纯色，同时亮起的键各自保持颜色；重复点击同键也换色。单色使用 `PressColor` 的 RGB，未设置时为青色 `(0, .8, 1)`。
- `PressBrightness` 范围 0～1，默认 1。按所选 RGB 线性缩放，0 不新建灯光；1 使用完整所选颜色和峰值不透明度，不乘旧的 `Opacity/Brightness/NeonSaturation`。未知复杂皮肤无法提取字形时仍降低覆盖率保护文字。不能超过屏幕显示亮度；单色选得暗时不会擅自改变它。
- 仅轻弹模式使用这三项。原三星扩散、圆环、键帽底色和 QQ 路径不变，不重写用户其他设置。主设置页有 36 个控件、15 份滑条说明，选色复用已验证的系统选色器。
- 跨 App 同步沿用 v2 完整性校验：扩展占用 word1 的 41～44 位、word14 高32位，以及 word2～4 各自高16位。原17个数字、4组颜色、10个开关的位位置不变；旧客户端忽略扩展，新客户端收到不含扩展的完整快照使用默认值。
- 回归检查颜色字段不覆盖旧字段、非法数据拒绝、单色重复点击、彩色逐次换色、多个键不同色、独立亮度、设置保存和独立进程恢复。系统键盘截图另检查单色强光、暗光、彩色多键的均匀像素与字形。仍需 iOS 17.0 真机与微信输入法确认。

## Samsung5 兼容性修订

- 前两版只处理单个 `UIKBKeyView` 的缓存，且明确排除了微信键盘。现在原生键盘额外处理 iOS 17 的 `UIKBKeyplaneView` / `UIKBSplitImageView` 整图路径：背景、边界与字符缓存分开处理，不把整张键盘字符一起涂黑。
- 整图缓存支持至 4096×2048、总像素不超过 2,097,152；不再套用单键的 1024×512 上限。字符与键帽混合图按不透明连通区域识别灰色/蓝色键身，分别消除底色，保留字形和 alpha。图片、背景色修改都有缓存与还原。
- 微信键盘在输入法控制器布局和键盘触摸时识别按键视图，处理其背景色、按键图片、普通及富文本字符。图片/颜色刷新后重应用，关闭开关恢复最后一次皮肤值。候选栏、工具栏不作为键帽处理，离开按键树的复用视图不继续染色。未识别的自定义整屏绘制或未知图像格式不会盲目覆盖。
- “纯黑键帽与底色（原生/微信）”沿用原配置键，两个键盘分别服从各自开关。跨进程配置补上微信键盘开关，纯黑模式的键缝遮罩也覆盖微信。
- 设置增加“复制键帽诊断”：只复制构建版本、系统版本、原生/微信最近上报的接口状态与处理计数，不复制输入、候选词或图像。计数上限 255；没有报告表示本版未收到该键盘上报，不等同于已证明无法注入。

本机只有 iOS 26.5 模拟器，没有 iOS 17.0 真机或微信输入法可运行副本。整图路径及微信视图使用专项测试夹具验证，模拟器系统键盘另做集成验证；不能将这些测试声称为 iOS 17.0 / 微信真机通过。安装后分别打开两个键盘输入几次，若仍灰，请在本插件设置中“复制键帽诊断”并反馈。

## 本次修改

- 默认使用键位扩散：周围键框按距离依次发光、退色。纯黑模式不再给按下或相邻键面填色。
- 背景霓虹沿真实键缝扩散。纯黑模式取消键面微光，并对整个光波（包括模糊阴影）使用键帽反向遮罩，连续输入的叠加光效也不会把黑色键面染成紫灰色。关闭纯黑模式仍保留上一版的键面微光。
- 原生键盘的底板和独立不透明键帽层均使用 RGB `(0, 0, 0)`；键帽及背光共享同一几何路径，白色字符保持原生绘制。微信输入法的已识别键帽也启用纯黑处理。视频受曝光影响，不能据此断言三星原版的精确 RGB。
- 修复上一版只处理 `Return-Key` 的遗漏：现在检查原生 `UIKBKeyView` 的字母键、空格键、功能键及其嵌套缓存图层，同时处理占主要面积的灰色底图和零红通道蓝色底图。灰色底图按行估算底色并反解白色字形的混合值，保留抗锯齿、彩色字符及圆角透明度，不把白字一起涂黑。每层只缓存最近一张转换图，关闭主题还原原图；纯字形、未知底色和超过 1024×512 的图像不修改。
- 监听系统专用 `_UIKBKeyViewLayer` 的缓存图赋值，避免后续刷新重新覆盖黑色；补上键盘类延后加载的安装重试，布局、填充和显示接口分别检查签名。UIKit 图片、颜色与字符更新 hook 仅处理已识别并标记的键盘子树，不全局修改应用图片或文字。
- 彩色边框改为键帽外侧的实心渐变环，普通键宽 2.6pt、按下键宽 3pt；不再用会被纯黑遮罩裁掉一半的细描边。背景扩散和颜色浓淡设置保留，键面仍为纯黑。
- 新增“霓虹颜色浓淡（浅→浓）”，范围 0～1，默认 0.72；低值偏浅淡，高值偏浓艳，0 为无彩色白光。与独立的“霓虹亮度（暗→亮）”共同调节，覆盖键框、背景扩散和旧版圆环，不改变纯黑键面与候选词渐变。柔和预设使用 0.4，鲜艳预设使用 1。
- 原生键盘通过 `keyplane.keys` 获取实际几何信息，调用前检查接口签名；第三方键盘从可识别的按键视图获取位置。不硬编码全键盘或九宫格，未识别到键位时不绘制。
- 支持切换回原版圆环。保留颜色、强度、传播时间、范围、同时光效数量等参数。
- 微信原实现是 `WBTextItemLabel` 的候选词内部横向渐变，默认 RGB 起点 `(0, 0.65, 1)`，终点 `(0.85, 0.15, 1)`。
- 原生候选词与微信共用同一渐变函数及颜色设置。除候选区中的 `UILabel`、`NSString` / `NSAttributedString` 外，修复了直接使用 CoreText 绘制的 `TUICandidateLabel`：提取实际字形透明度，按词的实际着墨宽度着色。
- 英文预测栏的 `TUIPredictionViewCell` 原先使用逐字缓存图片的 `UIMorphingLabel`，会绕过文字绘制 hook。开启原生渐变时改用 UIKit 已有的普通标签路径，保留布局和选择行为，但不保留逐字变形动画。
- 渐变仅影响候选词、预测词，不给搜索按钮、键帽字母、应用输入框或聊天消息染色。私有接口先检查签名，支持 TextInputUI 延后加载。
- 候选词渐变在没有历史设置时默认开启；已经明确关闭的设置不会被强制覆盖。

## 设置

只保留 `RainbowKeyboardPrefs` PreferenceBundle 的完整设置入口。旧 simple-plist 入口已删除，它的 8 个有效选项在完整页全部保留，沿用同一个偏好设置域和配置键，不清空已有设置。更新后如设置 App 仍显示缓存的两个入口，关闭设置 App 后重新打开。

主设置页的“光效样式”选择“三星风格键位扩散”，开启背景传播及背景霓虹扩散，可调扩散光强度。“自定义键帽与底色（原生/微信）”控制颜色主题；下面分别选择“键盘底色”“键帽颜色”，两项都选黑色即恢复纯黑。关闭主题后恢复原皮肤。效果预设保留自定义底色与键帽色。候选词渐变需要同时打开“候选词渐变”及“原生候选词”。

安装更新后重新启动使用键盘的应用；切换纯黑主题或首次启用预测词渐变后也应重开应用，以重建系统缓存键帽和预测标签。若旧键盘进程仍驻留，可在安装器中执行重新载入界面。

## 构建

使用已有 Theos 和 iOS SDK：

```sh
THEOS="$HOME/theos" gmake -j4 package ARCHS=arm64 THEOS_PACKAGE_SCHEME=rootless FINALPACKAGE=1
```

RootHide 必须使用 RootHide 版 Theos，选择 `ARCHS=arm64e THEOS_PACKAGE_ARCH=iphoneos-arm64e THEOS_PACKAGE_SCHEME=roothide`；不要直接把 Rootless 包重命名成 RootHide 包。

GitHub Actions（`.github/workflows/build.yml`）已改为纯 Rootless 构建：macOS runner 上安装 Theos + iPhoneOS16.5 SDK，执行 `ARCHS=arm64 THEOS_PACKAGE_SCHEME=rootless make package FINALPACKAGE=1`，产物为 `build/RainbowKeyboard-rootless.deb`（Actions 页面可下载）。

## 验证和边界

```sh
bash Tests/run-simulator.sh BOOTED_SIMULATOR_UDID
bash Tests/run-simulator.sh BOOTED_SIMULATOR_UDID --native-keyboard
bash Tests/run-simulator.sh BOOTED_SIMULATOR_UDID --native-colors

```

测试在 iOS 模拟器中运行同一份光效实现和由 Logos internal generator 生成的候选词、纯黑主题 hook。覆盖两端渐变像素、微信/原生一致性、独立开关、普通应用不染色、自绘文字、键位过滤、未知 ABI、连打上限、未知布局、旧模式、扩散延迟、背景光开关与像素、图层回收。

还验证真实系统 `TUICandidateLabel` 的中文渐变及真实 `UIKBBackdropView` 的不透明纯黑像素；检查不透明键帽、重叠光波期间键面保持纯黑、粗边框宽度，以及搜索键缓存去蓝和恢复。灰色回归覆盖三种底色、纵向底色渐变、嵌套图层、白字和抗锯齿、彩色字符、圆角透明度、缓存复用、关闭恢复和原生图层赋值。`--native-keyboard` 打开系统键盘和固定测试词，输出整键盘截图、实际键位上的光效截图 `native-wave.png`、所有实际键帽的像素统计、预测绘制计数和实际键位数。输出在测试 App 的 `Documents` 目录。

这些包含 UIKit 测试夹具和模拟器系统组件验证，但不等同于真实微信输入法或越狱设备验证。不同 iOS 版本和越狱注入机制仍需真机确认；未知接口会跳过，不盲目 hook `renderCandidateWord:focusedStyle:atIndex:`。

原生渐变诊断写入 `/var/mobile/Library/Preferences/RainbowKeyboard-native-probe-<应用标识>.plist`，无权限时回退到进程临时目录。只记录系统版本、绘制类名、接口和开关状态、绘制计数，不记录用户输入或候选词内容。

纯黑诊断写入相同目录的 `RainbowKeyboard-black-probe-<应用标识>.plist`，记录接口安装状态、视图/图层类名及灰色/蓝色图像处理数量，不记录按键名称、输入内容或图像。若真机仍灰，请附此报告及 iOS/键盘类型，以区分未注入、接口差异和其他皮肤插件的绘制覆盖。

真机验收应检查原生拼音全键盘、九宫格、英文预测、展开候选栏、微信输入法、横竖屏、浅色/深色、连续输入和开关恢复。若某个候选区仍是原色，需要提供 iOS 版本、越狱类型、键盘类型及效果录屏，再针对其实际绘制路径适配。
